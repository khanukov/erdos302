### 1.2 Build / install (standalone lean4checker, tag v4.27.0)

- README at v4.27.0 [l4c_v4270_README.md]: "To run this in another Lean project, use: `lake env path/to/lean4checker` or `lake env path/to/lean4checker Mathlib.Data.Nat.Basic` to check a single file." - README caveat (VERIFIED): "Despite `.olean` files being 'fairly cross-platform', `lean4checker` will reject `.olean`s that were compiled on a system that does not use the same bignum library as your system, so it advisable to not rely on cached `.olean`s." (This is the GMP flag bit in the olean header, §3.2.)

### 1.3 CLI (verified from `Main.lean`, identical at v4.27.0 and master)
- Args are split into flags (start with `-`) and module names. `-v`/`--verbose`; `--fresh`; `--num-workers=N` (default 8). No `--compare` (that is lean4lean-only).
- Module arguments are **prefixes**: "for path in (← SearchPath.findAllWithExt sp "olean") … if target.isPrefixOf m then targetModules := targetModules.insert m". So `lean4checker Erdos302.Asymptotic` checks every module whose name starts with `Erdos302.Asymptotic` (including `Erdos302.Asymptotic.Endpoint` etc.). With no argument it checks the package named in `lake-manifest.json` (`getCurrentModule`). Note the search path includes Lean core and all dependencies, so `lean4checker Mathlib` would check Mathlib's ~7000 modules individually.
- `--fresh`: "if targetModules.length != 1 then throw … `--fresh flag is only valid when specifying a single module`". Implementation: `replayFromFresh`: `Lean.withImportModules #[{module}] {} fun env => do discard <| (← mkEmptyEnvironment).replay' env.constants.map₁` — i.e. import the module (and thereby its whole transitive closure) into memory, then replay **every** constant of the resulting environment into an empty kernel environment. Single-threaded.
- Non-fresh mode (`replayFromImports`): reads the module's `.olean` (+ `.olean.server`, `.olean.private` if present), calls `importModulesCore mod.imports` + `finalizeImport`, then replays only the constants of that one module on top of the (trusted) imported environment. Runs modules in parallel with a sliding window of `--num-workers` tasks. Doc-comment: "We use a conservative default to avoid OOM on machines with 32GB RAM when checking large projects like Mathlib, where each worker loads a near-complete environment."
- Main docstring: "This is not an external verifier, simply a tool to detect 'environment hacking'." and "Contributor's note: lean4lean is intended to have a CLI interface matching lean4checker".
- Exit behaviour: on kernel rejection it prints `lean4checker found a problem in {m}` and rethrows the `IO.userError` (non-zero exit); success returns 0 with no per-declaration output (unless `-v`, which only prints per-module lines).

### 1.4 What replay checks (Lean.Replay at v4.27.0, and lean4checker's patched `replay'`) — VERIFIED from source
- `Lean/Replay.lean` [lean4_v4270_Replay.lean]: for every constant (in dependency order via `getUsedConstantsAsSet`) it rebuilds a `Declaration` from the stored `ConstantInfo` and calls `env.addDeclCore 0 d` (trust level 0 → full kernel type-check). Theorems/defs/axioms/opaques are re-checked; inductives are re-added via `Declaration.inductDecl`, and constructors/recursors are **not** sent to the kernel but instead compared for equality with what the kernel regenerated: "if ! (info == info') then throw <| IO.userError s!"Invalid recursor {ctor}"". Quotient constants trigger `Declaration.quotDecl`.
- **Skipped**: "We skip unsafe constants, and also partial constants." (`if !ci.isUnsafe && !ci.isPartial`). Since a theorem cannot depend on an unsafe/partial constant without the kernel rejecting it, this does not weaken theorem checking, but it means `unsafe`/`partial` definitions are not re-checked.
- lean4checker's own `Lean4Checker/Replay.lean` [Lean4Checker_Replay.lean] is a "patched version of `Lean.Environment.Replay`" that (a) works on `Kernel.Environment`, (b) tolerates duplicate private theorems from the module system ("Ignore duplicate theorems … we might encounter duplicate private theorems"), and (c) replays `Eq` before `quotDecl` ("`Quot.lift` and `Quot.ind` have types that reference `Eq`").
- Axioms: replay adds `axiomDecl`s without complaint. **It does not check which axioms are used** (see Zulip "Checking axioms with leanchecker", Eric Wieser 2025-05-02: "Could leanchecker learn a flag to forbid axioms beside the standard axioms (especially sorry)?" — no such flag exists in `Main.lean`). `#print axioms` (or comparator / nanoda's `permitted_axioms`) remains necessary. Also note `Lean.CollectAxioms.collect` [src_Lean_Util_CollectAxioms.lean] walks `env.checked.get.find? c` — it reads the constant bodies from the (imported) environment; it is a traversal of the stored terms, not a kernel check.
- Does NOT check: theorem *statements* against anything external; `.olean` structural integrity ("It trusts that the .olean files are structurally correct" — reference manual, below); anything that happened at elaboration time (tactics, `implemented_by`), and it cannot validate `Lean.ofReduceBool`/`native_decide` proofs ("External checkers (lean4checker, comparator) cannot check such proofs, as they do not have access to the Lean compiler." — reference manual).

### 1.5 Official guidance — "Validating a Lean Proof" (Lean reference manual, https://lean-lang.org/doc/reference/latest/ValidatingProofs/) — VERIFIED quotes
- "Build your project using lake build, run lean4checker --fresh on the module that contains the theorem of interest, and check that no error is reported."
- "The lean4checker tool reads the declarations and proofs as they are stored by lean during building (the .olean files), and replays them through the kernel. It trusts that the .olean files are structurally correct."
- Trust: "This check is meaningful if one believes the formal theorem statement corresponds to its intended informal meanings and believes the authors of the imported libraries to not be very cunningly malicious, and to neither compromise the user's system nor use Lean's extensibility to change the interpretation of the theorem statement."
- Protection (beyond blue ticks / #print axioms): "Bugs in Lean's core handling of the kernel's state (e.g. due to parallel proof processing, or import handling)"; "Meta-programs or tactics intentionally bypassing that state (e.g. using low-level functionality to add unchecked theorems)".
- Comments: "Since lean4checker reads the .olean files without validating their format, this check is prone to an attacker crafting invalid .olean files (e.g. invalid pointers, invalid data in strings)." … "We recommend running lean4checker as part of CI … The lean-action GitHub Action provides this functionality by setting lean4checker: true." … "Without the --fresh flag the tool can be instructed to only check some modules, and assume others to be correct (e.g. trusted libraries), for faster processing."
- Gold standard: "At the time of writing, comparator supports using the official Lean kernel and the external checker nanoda, which is developed independently and implemented in Rust. The Lean Kernel Arena features more external checkers that can be used manually for even more confidence." Remaining assumptions with comparator: "The soundness of Lean's logic. The plumbing provided by the comparator tool is correct. The sandbox used by comparator is secure. There is no implementation bug affecting all of the used checkers simultaneously. No human error or misleading presentation of the theorem statement in the trusted challenge file."

### 1.7 Sharding
- Non-fresh mode accepts any list of module-name prefixes and parallelises internally; a job matrix can pass disjoint prefixes (e.g. `Erdos302.Certificates.Batch1`, …) — each shard re-imports the trusted closure and checks only its modules. VERIFIED from `Main.lean`.
- `--fresh` cannot be sharded: exactly one module, single-threaded, and it re-checks the entire closure (Init/Std/Lean/Mathlib included) every time. INFERRED: for a project whose closure includes Mathlib, `--fresh <root>` ≈ 40–50 min of kernel time for Mathlib alone (arena: 43 min for the C++ kernel over the export) plus the project's own constants; the 80,000 generated certificate modules add their constants once (not per module), so `--fresh` cost is proportional to the number of constants, not modules. Non-fresh sharded checking of only the project's modules over a trusted Mathlib is what Mathlib itself considers adequate for PR CI (the daily `--fresh` run covers the rest).

### 1.8 Known failure modes (not soundness bugs)
- lean4checker can fail for reasons unrelated to proof validity: Zulip "lean4checker failure" (2024-12-03): "uncaught exception: parser 'subscript' was not found" on `Mathlib.Geometry.Manifold.BumpFunction` — caused by a `register_parser_alias` initializer not being run under `withImportModules (loadExts := false)`. Kim Morrison: "Lesson: we need to be running lean4checker against nightly-testing, too!". Relevant because this project's generated modules use Mathlib tactics; a failing replay must be diagnosed, not assumed to be a soundness finding.
- Zulip "leanchecker failure" (2026-01-27) shows a bot failure post followed by "Hopefully #34480 will improve matters" (Mathlib PR) — i.e. Mathlib-side fixes are sometimes needed.

## 2. Independent / external kernels

### 2.1 Input formats — the fundamental split (VERIFIED)
- `.olean` consumers: lean4checker/leanchecker and lean4lean (default modes). They mmap the compacted object graph produced by the C++ `object_compactor` and trust its structure.
- NDJSON export consumers: nanoda and all Lean Kernel Arena checkers, fed by **lean4export** (https://github.com/leanprover/lean4export): "lake env <path to lean4export binary> <lean file without .lean suffix>+", e.g. "lake env ../.lake/build/bin/lean4export Mathlib > out.ndjson" — "This exports the contents of the given Lean module …, and its transitive dependencies." Options `--export-unsafe`, `--export-mdata`. Export format "version 3.1.0" (`format_ndjson.md`, identical header at tag v4.27.0), beginning with a `meta` object carrying exporter/Lean versions and githash. lean4export has a tag for every Lean release since v4.15.0, including **`v4.27.0`** (its `lean-toolchain` = `leanprover/lean4:v4.27.0`) [git ls-remote; lean4export_v4270_toolchain]. lean4export itself imports the `.olean`s via the Lean runtime (so the exporter shares the .olean-deserializer trust; comparator therefore runs it inside a sandbox).
- Export size/cost: Arena's Mathlib test is a 5.2 GB, 100.0 M-line NDJSON file; WebSearch summary of a Zulip report (not primary-verified): writing a 37.8 GB export (older format) "takes about 90 GB of memory for an hour", nanoda check "about 40 GB (about 30 minutes at 16 threads)" — treat as UNKNOWN/dated. The arena's current numbers (§2.3) are the reliable ones.

### 2.2 lean4lean (Mario Carneiro) — https://github.com/digama0/lean4lean
- README [lean4lean_README.md] VERIFIED: "This is an implementation of the Lean 4 kernel written in (mostly) pure Lean 4. It is derived directly from the C++ kernel implementation, and as such likely shares some implementation bugs with it (it's not really an independent implementation), although it also benefits from the same algorithmic performance improvements existing in the C++ Lean kernel."
- Build/run: "`lake build lean4lean` (note the capitalization!) builds the `lean4lean` command line tool"; "After `lake build lean4lean`, the executable will be in `.lake/build/bin/lean4lean` … you should evaluate it like `lake env .lake/build/bin/lean4lean`" from the target project's directory. CLI: "`lean4lean [--fresh] [-v|--verbose] [--compare] [MOD]`" — `MOD` "an optional lean module name … If provided, the specified module will be checked (single-threaded); otherwise, all modules on the Lean search path will be checked (multithreaded)"; `--fresh` "the module and all its imports will be rebuilt from scratch, checking all dependencies of the module"; `--compare` "If lean4lean takes more than a second on a given definition, we also check the C++ kernel performance". `Main.lean` on master also has `--config=<file>` / `--config:<field>=<value>` fuel options and, on the `arena` branch, an `--import "$IN"` mode that reads NDJSON (arena checker metadata: `"run": ".lake/build/bin/lean4lean --import \"$IN\""`).
- Version coupling (VERIFIED): master `lean-toolchain` = `v4.33.0-rc2`; branches `v4.27.0-rc1` and `arena-v4.27.0-rc1` exist with `lean-toolchain` = `leanprover/lean4:v4.27.0-rc1` — **no branch/tag for v4.27.0 final**. Arena metadata: "The lean4lean checker checks that primitive definitions from the prelude are as expected, so it is sensitive to the Lean version it is built against." INFERRED: lean4lean's .olean mode must be built with the same toolchain that produced the .oleans (header format byte; GMP flag; Lean API), so using it on v4.27.0 .oleans would require rebasing the `v4.27.0-rc1` branch onto v4.27.0 — feasible (rc1→final rarely changes the olean format) but not off-the-shelf. Its NDJSON `--import` mode only depends on the export format, and could consume a v4.27.0 export produced by lean4export v4.27.0.
- Maturity/verification: paper "Lean4Lean: Verifying a Typechecker for Lean, in Lean" (arXiv 2403.14064, v3 2025-09-14, CPP 2026): "the first complete typechecker for Lean 4 other than the reference implementation in C++ … running between 20% and 50% slower and usable to verify all of Lean's mathlib library"; verification is partial ("only a few functions from the typechecker have been verified, like `inferLambda`"; unique typing etc. are conjectures). `bugs-found.md` lists three kernel bugs found via the formalization (a `hasLooseBVars` soundness bug thread; lean4 issues #10475, #10511).
- Performance (VERIFIED quotes): Zulip 2023-10-30 Scott Morrison: "lake env ../lean4lean/build/bin/lean4lean --fresh Mathlib 1752.20s user 137.67s system 99% cpu 31:33.01 total" "(Compared to 21 minutes from the C++ kernel. Nice!)". Earlier (2023-10-20): lean4checker `--fresh Mathlib` "21:15.51 total" while lean4lean was "still running with 4 hours on the clock" before performance bugs were fixed; Mario (2023-10-27): "without [--fresh] one has to be careful to limit the number of threads or it uses up all my memory building 12 copies of mathlib in memory." Arena 2026-09-09: lean4lean on the Mathlib export: wall 2477 s (41.3 min), max RSS 9.94 GB (vs official 2570 s / 8.16 GB) — i.e. now on par with the C++ kernel.

### 2.3 nanoda / nanoda_lib (Chris Bailey, Rust) — https://github.com/ammkrn/nanoda_lib
- README (`master`) VERIFIED: "This is an external type checker for the Lean 4 programming language and theorem prover." "Either run the binary directly through cargo `cargo run --release -- <path_to_config>`, or build the binary using `cargo build --release`, then run the built binary, passing a path to a configuration … Export files can be streamed via stdin … by setting `use_stdin: true`". "Export files can be created with lean4export." Configuration is a JSON file ("there is no old school CLI") with `export_file_path`/`use_stdin`, `permitted_axioms` (must list `propext`, `Classical.choice`, `Quot.sound`; "most export files will also rely on `Lean.trustCompiler`" because `Init` defines `Lean.reduceBool`/`reduceNat` via `have := trustCompiler` — Zulip "Why does the daily Nanoda check allow `Lean.trustCompiler`?", Chris Bailey 2026-01-09), `unpermitted_axiom_hard_error`, `nat_extension`, `string_extension` (kernel Nat/String literal extensions, "disabled by default"), pretty-printer options, `num_threads` (used in arena configs). Cargo.toml: `nanoda_lib` version 0.4.17, Apache-2.0, binary `nanoda_bin`.
- Independence: clean-room in the sense of a separate code base (not derived from the C++ kernel), reads only the export; the reference manual names it as comparator's supported external checker. Arena scoreboard (2026-09-09): nanoda `master (4c544ed)` has 7 wrongly-rejected valid tests and 2 declined (66/73 rejects correct) — it is not the top-scoring fork; `sokonanoda` (Apache-2.0 fork by intgrah), `mathgraph`, `nanoclo`, `nanobruijn`, `still-nanoda`, `zignodamus` (Zig) are nanoda-derived; `eink0rn` (Haskell, clean-room), `rpylean` (RPython), `kiota` (Rust from scratch), `nyaya` (OCaml), `vow-lean-kernel`, `evmlean` (Solidity) are other independent implementations; `ind-models` (nomeata) re-derives inductive recursors on top of the official kernel.
- Arena Mathlib-export results (VERIFIED from results.json; 4 threads where applicable): nanoda wall 479 s / CPU 1642 s / RSS 7.9 GB; sokonanoda 60 s / 212 s / 7.2 GB; nanoclo 250 s / 822 s / 7.1 GB; still-nanoda 239 s / 688 s / 5.6 GB; official 2570 s / 8.2 GB; lean4lean 2477 s / 9.9 GB. All of these accepted all 670,627 Mathlib declarations, and all pass 73/73 reject tests except nanoda (66) and a few others.
- Mathlib uses nanoda daily (VERIFIED indirectly: the Zulip thread quotes "The JSON configuration for the daily Nanoda check on Mathlib" with `"export_file_path": "mathlib_export.txt"`; lean-action exposes `nanoda: true` / `nanoda-allow-sorry`: "nanoda is an independent Lean 4 type checker written in Rust. Requires Rust toolchain (will be installed automatically if not present)." [lean_action_action.yml:121-128]).

### 2.4 comparator (Lean FRO) — https://github.com/leanprover/comparator
- README VERIFIED: "Comparator is a trustworthy judge for Lean proofs." Requires `landrun` (sandbox), `lean4export` "at a version that is compatible with whatever Lean version your project is targeting", optionally `nanoda_bin`. JSON config with `challenge_module`, `solution_module`, `theorem_names`, `permitted_axioms`, optional `external_kernels` ("Comparator will execute the command described by the `mykernel` array and additionally pass a file, containing the solution export"). Guarantees: theorems "1. Prove the same statement as provided in `Challenge` 2. Use no more axioms than listed in `permitted_axioms` 3. Be accepted by the Lean kernel". Internals: "We generally adopt a policy of not loading olean files as they just get mmaped into our address space and then dereferenced and are as such a potential point of attack for sophisticated adversaries." Steps: sandboxed `lake` build of Challenge, sandboxed lean4export, same for Solution, then "Verify that all declarations used in the statement of all relevant theorems in `Challenge` are the same as in the `Solution` environment", axiom check, "Replay the `Solution` environment into the Lean kernel." Also: "running `lake exe cache get` to download a Mathlib cache is acceptable before running the comparator if you trust the cache to not be modified".
- This is the officially documented way to assert "statement X in trusted file == statement proved" (relevant to plan item P4); it needs a lean4export matching the project's Lean version (v4.27.0 tag exists) and Linux with Landlock (`landrun`).

### 2.5 Other tools
- `lean-action` (https://github.com/leanprover/lean-action) inputs: `leanchecker`, `leanchecker-args` ("`leanchecker-args: "MyPkg.Core MyPkg.Extras"` restricts checking to the listed module prefixes"), deprecated alias `lean4checker`, `nanoda`, `nanoda-allow-sorry`, `axiom-audit` (https://github.com/leanprover-community/axiom-audit: "checks that every declaration in your library depends only on an allowlist of axioms … Because it inspects the compiled kernel environment, it catches … `sorry`/`admit` (`sorryAx`), `native_decide` (`Lean.ofReduceBool`), and any home-rolled `axiom`").
- SafeVerify (GasStationManager) — lean4checker-based with an axiom check; Zulip notes its use of `CollectAxioms.collect` "is shown to be unreliable" in a specific adversarial example (2025-05-02). Not further verified.
- Lean 3 era tools (`trepplein`, `leanprover/tc`, Lean 3 `leanchecker`) do not apply to Lean 4.

## 3. Lean's own facilities and what `import` guarantees

### 3.1 `lean` CLI (v4.27.0 `Lean/Shell.lean` help text, VERIFIED)
- `--run <file>` "call the 'main' definition in the given file with the remaining arguments"; `--stdin` "take input from stdin"; `-o, --o=oname` "create olean file"; `-t, --trust=num` "trust level (default: max) 0 means do not trust any macro, and type check all imported modules"; `--json`; `--setup=file` "JSON file with module setup data (supersedes the file's header)"; `--deps`.
- **The `--trust=0` help text is misleading in Lean 4** (INFERRED, strong): `trustLevel` is only stored in `EnvironmentHeader.trustLevel` ("the kernel assumes imported constants are type correct when the trust level is greater than zero" — Environment.lean:162) and compared against `LEAN_BELIEVER_TRUST_LEVEL 1024` ("If an environment E is created with a trust level > LEAN_BELIEVER_TRUST_LEVEL, then we can add declarations to E without type checking them." — kernel/environment.h:21). Grepping `Environment.lean`, `kernel/environment.cpp`, `kernel/type_checker.cpp`, `kernel/inductive.cpp` finds no code path that re-type-checks imported constants at trust level 0; imported constants are always inserted into the constant map unchecked by `finalizeImport`. Re-checking imports is exactly what `lean4checker --fresh` exists for.
- `#print axioms` (`Lean.Elab.Print` / `CollectAxioms`): traverses `ConstantInfo` values from the imported environment; it reports what the stored terms reference and does not itself type-check. `lake env lean --stdin` with `import X` + `#print axioms X.thm` therefore verifies (i) the constant exists with that name in the imported .olean, (ii) its stored body transitively uses only the listed axioms — nothing about whether the body type-checks.

### 3.2 What importing a `.olean` verifies (v4.27.0 `src/library/module.cpp`, `Lean/Environment.lean`) — VERIFIED
- On-disk header (`module.cpp:76-105`): 5-byte marker `"olean"`, 1-byte format `version = 2`, 1 byte `flags` ("bit 0: whether persisted bignums use GMP or Lean-native encoding"), 33-byte `lean_version` string, 40-byte `githash`, `base_addr`, then the compacted object graph.
- Checks performed by `readModuleDataParts` (`module.cpp:244-257`): marker must match ("invalid header"); `header.version != default_header.version || header.flags != default_header.flags` → "incompatible header"; the **githash is compared only `#ifdef LEAN_CHECK_OLEAN_VERSION`**, which is the CMake option `CHECK_OLEAN_VERSION "Only load .olean files compiled with the current version of Lean" OFF` (`src/CMakeLists.txt:90`, listed under "development-specific options"); the release CI's `CMAKE_OPTIONS` in `.github/workflows/ci.yml` do not set it. The `lean_version` string is not compared at all. INFERRED: release toolchains accept any `.olean` with the right magic, format byte and GMP flag regardless of which Lean commit produced it; a version mismatch typically manifests as a crash or garbage, not a clean error.
- Then the file is `mmap`ed at `base_addr` (falls back to read+relocate). **No checksum, hash, signature, or size validation of the payload exists**; object pointers inside are trusted (hence the manual's "invalid pointers" remark and comparator's refusal to load oleans).
- At the Lean level (`Environment.lean:1996-2260`): `importModulesCore` resolves each `Import` by module *name* through the search path (`findOLean`), recursively; `finalizeImport` builds the constant map and only rejects duplicate constant names: "import {modName} failed, environment already contains '{cname}' from {constModName}". A module's `ModuleData` stores `imports : Array Import` (names only) — there is **no hash of the imported modules' contents**, so an importer's `.olean` does not pin the exact `.olean`s of its dependencies. Consistency across a mixed set of `.olean`s (e.g. overlay + freshly compiled) is not checked by Lean; it is Lake's job.
- Lake (v4.27 `Lake/Build/Common.lean`, `Build/Module.lean`, VERIFIED): rebuild decisions compare the input-dependency hash `depTrace.hash == depHash` stored in the `.trace` JSON next to the artifact (plus existence of the output; `--old` uses mtimes); artifacts' own hashes are cached in `.hash` files (`cacheFileHash mod.oleanFile`) for the artifact cache; `--rehash` recomputes. So Lake trusts the `.trace`/`.hash` files as given, and a consistent tree of `.olean`+`.trace` files (as in the overlay) is accepted without re-reading sources. Lake does not verify that an `.olean`'s content corresponds to the trace.

### 3.3 Consequences for the "replay makes provenance irrelevant" principle (INFERRED, with the verified facts above)
- `lean4checker --fresh <Root>` (or a matrix of non-fresh shards + one trusted-closure `--fresh`) does re-run the kernel on every non-`unsafe`/`partial` constant present in the environment, so a `.olean` that stores a *type-incorrect* proof, or a theorem whose stored proof term does not have the stated type, is rejected regardless of where the `.olean` came from. This covers the "kernel + .olean deserializer + toolchain" residual described in the plan, matching the reference manual's description.
- What replay does **not** cover, and what the plan must handle separately: (a) the *statements* — replay checks the stored `type` of `f302_upper_…` type-checks as a Prop and its stored value inhabits it, but not that the stored `type` equals the intended text; that requires either compiling the statement-defining modules from source in the same run and using *those* `.olean`s in the replayed closure (P1), or a comparator-style export comparison against a trusted challenge (P4); (b) `.olean` structural integrity — an adversarially crafted `.olean` can crash or subvert the process that mmaps it (manual; comparator); a deterministic-rebuild + SHA-256 equality check of every `.olean` (P1's second option) or replaying from an NDJSON export (nanoda/comparator) closes this; (c) `unsafe`/`partial` constants are skipped by replay (irrelevant for theorems, since the kernel forbids theorems from depending on them); (d) axioms are accepted by replay — `#print axioms` on the final theorem in the *replayed* or freshly compiled environment remains required; (e) `Lean.ofReduceBool` proofs cannot be re-checked by any external tool — already excluded by repository policy (`scripts/audit_lean_sources.py`) and by the axiom audit.
- Determinism claim in P1 ("Lean compilation is deterministic, so SHA-256 equality is expected"): UNKNOWN/not verified here. Note the header embeds `githash`, `lean_version` and a `base_addr` derived from the module name hash — stable for a fixed toolchain and module name — but Lake's `.olean.server`/`.olean.private` parts, `-D` options, and the module system can change output; the lean4checker README's GMP caveat also shows `.olean`s can differ across builds of the *same* Lean version if the bignum backend differs. A pilot comparison is required before relying on byte-equality.
